# EverGrow 项目设计与 API 说明（论文素材版）

## 1. 项目定位与研究目标

EverGrow 是一个面向家庭教育场景的 RAG（Retrieval-Augmented Generation，检索增强生成）问答系统。  
核心目标是让系统在回答亲子教育问题时，优先基于本地知识库给出可追溯答案，并在本地检索不足时自动触发联网补充，从而提升回答的相关性、可信度与覆盖率。

本项目适合用于毕业设计中的以下研究点：

- 教育垂直领域知识问答系统设计与实现
- 向量检索 + 关键词检索 + 重排的混合检索策略
- 基于年龄阶段（stage）的检索过滤与回退机制
- 多轮对话上下文管理与会话持久化
- 面向工程交付的统一异常返回、启动配置校验与健康检查

## 2. 系统总体设计思路

## 2.1 架构分层

系统采用前后端分离与模块化分层设计：

- 表现层：前端（EverBloom/Streamlit）负责用户交互、会话管理、流式渲染
- 接口层：FastAPI 路由对外提供认证、会话、RAG 问答等 HTTP API
- 业务层：RAG 检索与生成、鉴权、参数校验、异常处理
- 数据层：Chroma（向量库）+ MySQL（用户、会话、消息、文章元数据）

## 2.2 关键流程

### (1) 知识入库流程（离线）

1. 从 `data/raw` 读取 `txt/docx/doc` 文件
2. 解析正文并推断文章年龄段 `stage`
3. 按段落 + overlap 进行分块（chunking）
4. 生成 embedding 写入 Chroma
5. 同步写入 MySQL 元数据表（如标题、来源、stage、哈希等）

### (2) 问答流程（在线）

1. 前端提交问题（可带 stage、history、conversation_id）
2. 后端校验参数并解析登录态
3. 检索模块执行混合检索（向量 + 关键词）并重排
4. 若本地检索为空，则触发联网检索补充
5. 生成模块基于检索上下文流式输出回答
6. 返回 NDJSON：先 sources/meta，再持续 chunk
7. 若带会话 ID 且权限通过，则保存用户问题与助手回答

## 3. RAG 关键策略设计

## 3.1 年龄阶段（stage）机制

系统支持 `幼儿期/学龄前/小学/初中/高中/通用` 六类阶段：

- 入库阶段：从文件名、标题、内容规则匹配推断 stage
- 提问阶段：用户可手动指定 stage，未指定则由问题文本自动识别
- 检索阶段：按“目标阶段 -> 通用 -> 相邻阶段”进行回退检索

该策略可在保证垂直相关性的同时降低“无结果”概率。

## 3.2 混合检索与阈值过滤

检索模块组合两类信号：

- 向量检索得分（`vector_similarity`）
- 关键词召回得分（`keyword_score`）

在融合时引入：

- 标题命中加分
- 正文命中加分
- 回退层级优先级加分

并通过 `similarity_threshold` 与 `keyword_threshold` 做阈值过滤，最后选取 `rerank_k` 条用于生成。

## 3.3 分块策略（Chunking）

通过 `chunk_size` 与 `chunk_overlap` 进行控制，使用段落优先、超长兜底切分策略，兼顾：

- 召回粒度（块太大影响精确召回）
- 语义完整性（块太小导致上下文断裂）
- 生成稳定性（上下文更聚焦）

## 4. API 功能说明

统一前缀：

- 认证：`/api/auth/*`
- 会话：`/api/conversations/*`
- 问答：`/api/routes`

## 4.1 认证模块（Auth API）

### `POST /api/auth/register`

- 功能：用户注册并签发 JWT
- 请求体：`username`、`password`、`nickname(可选)`
- 返回：`access_token` + `user`

### `POST /api/auth/login`

- 功能：用户登录并签发 JWT
- 请求体：`username`、`password`
- 返回：`access_token` + `user`

### `GET /api/auth/me`

- 功能：获取当前登录用户信息
- 鉴权：`Authorization: Bearer <token>`

## 4.2 会话模块（Conversations API）

### `GET /api/conversations`

- 功能：分页获取会话列表
- 参数：`page`、`page_size`、`keyword`
- 特性：支持按标题关键词搜索

### `POST /api/conversations`

- 功能：创建会话（可带标题）

### `PATCH /api/conversations/{conversation_id}`

- 功能：重命名会话

### `GET /api/conversations/{conversation_id}`

- 功能：获取会话详情与历史消息

### `DELETE /api/conversations/{conversation_id}`

- 功能：删除会话

## 4.3 问答模块（RAG API）

### `POST /api/routes`（流式）

- 功能：RAG 问答（支持 stage、多轮 history、会话落库）
- 返回类型：`application/x-ndjson`
- 返回格式：
  - 首行：`{"sources":[...], "stage":"..."}`
  - 后续：`{"chunk":"..."}`

请求体示例：

```json
{
  "question": "孩子写作业总是拖拉怎么办？",
  "stage": "小学",
  "history": [
    { "role": "user", "content": "最近每天都要催很多次" },
    { "role": "assistant", "content": "先建立固定作业时间和番茄钟机制" }
  ],
  "conversation_id": 12
}
```

## 5. 参数校验与异常处理设计

## 5.1 参数校验

项目在 Pydantic 模型层做了严格校验：

- `question` 非空且长度限制
- `history` 条数限制与内容长度限制
- `stage` 使用枚举约束
- 会话与分页参数有最小/最大值约束

## 5.2 统一异常返回

系统采用统一错误结构：

```json
{
  "code": "ERROR_CODE",
  "message": "错误描述",
  "detail": {}
}
```

已覆盖：

- 业务异常（`HTTPException`）
- 参数异常（`RequestValidationError`）
- 未捕获异常（统一 `INTERNAL_ERROR`）
- 流式生成异常（`STREAM_ERROR`）

## 5.3 启动校验与健康检查

- 启动时调用 `validate_startup_config()`，校验 `.env` 与 `config/database.yml` 的关键字段
- `GET /health` 输出配置、数据库、Chroma 三项健康状态，便于部署与运维观测

## 6. 数据与存储设计（实现层面）

## 6.1 Chroma（向量库）

用于存储知识分块后的向量与元数据：

- 文本内容 `content`
- 标题 `title`
- 来源文件 `source_file`
- 年龄段 `stage`
- 分块序号 `chunk_index/chunk_total`

## 6.2 MySQL（结构化数据）

用于存储平台业务数据：

- 用户信息（账号、密码哈希、昵称、状态）
- 会话信息（标题、所属用户、更新时间）
- 消息信息（角色、内容、可选检索文档 ID 列表）
- 文章元数据（便于管理与追踪）
